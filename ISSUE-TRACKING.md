# Issue tracking for DevOps Sandbox

Итоги первой сессии (2026-11-03 — 2026-11-06): требования к трекеру, почему Plane CE не подошёл, план дальше.

## Цель

Вести roadmap и задачи DevOps Sandbox в нормальном трекере вместо текстового roadmap в `website/docs/roadmap`. Сайт остаётся статикой на GitHub Pages и содержит снапшот roadmap/задач, собираемый при релизе.

## Требования

### Обязательные

- **Open source, self-hosted**, запуск локально (Docker). Без платных функций в основном сценарии.
- **Версии как срезы зрелости (матрица «компонент × критерий»).** Система развивается слоями: заранее определяются *все* компоненты и *все* критерии роста, и каждая версия требует, чтобы каждый компонент дорос до своего набора критериев. Цель — не забывать компоненты и не развивать только любимые. Нативный объект Release не обязателен: релиз может быть вьюхой/срезом. Нужно *визуально* видеть, какие компоненты в версии X уже выполнили критерии, а какие отстают. Лейблы для этого не подходят.
  - Нужно: задать список компонентов и критериев, привязать задачи к паре «компонент + критерий» и к целевой версии, собрать представление-срез по версии.
  - 0.1.0 Self-hosted Kubernetes
  - 0.2.0 Self-hosted multi-cluster
  - 0.3.0 Common EKS
  - 0.4.0 Staging EKS
  - 1.0.0 Platform App Library
- **Несколько проектов** под одним зонтиком: Infra, GitOps Platform, Wiki, Website, System Map (схема: `website/docs/.diagrams/devops-sandbox-overview.mmd`).
- **Надёжный API**: создание и изменение проектов, модулей/компонентов, задач, описаний и страниц без потери данных.
- **Экспорт** задач и roadmap (JSON/Markdown) для статического снапшота на сайте.
- **Страницы/документы внутри проекта**: Metadata (конвенции) и Releases (критерии готовности версии).

### Модель данных

- Модуль/компонент = конкретный tool или distro (например `PostgreSQL / CloudNativePG`, `Elasticsearch (ELK)`). Как в docs: теги `category`, `tool`, `distro`.
- Категории (Observability/Logs и т.п.) — лейблы.
- На каждый tool — полный список задач на реализацию его requirements. Задачи общие, не точечные.
- Релиз можно выразить как модуль вида `/ Release 0.2.0` (слэш в именах, не точки; релизы сортируются наверх), поле, initiative или вьюху: подойдёт всё, из чего собирается срез по версии (см. требование про матрицу).
- Короткие лейблы; `runtime` вместо `environment`; в разделителях дефис вместо точек.
- У каждого проекта страницы **Metadata** (какие лейблы и группы, по какому признаку делятся модули, requirements) и **Releases** (критерии готовности, например «все tools соответствуют requirements»).

### Желательные

- Desktop/PWA клиент.
- Конвенции дублируются в репозитории, чтобы не зависеть от трекера.
- Позже: интеграция с Wiki (кандидат Outline) и с React Flow схемой.

## Почему Plane CE не подошёл

Plane CE v1.4.3 был развёрнут локально и частично заполнен (позже удалён вместе со своими файлами). Отказались по причинам:

- Нет Releases, Initiatives, Milestones (только Commercial). Версии эмулируются модулями и Workspace Views.
- Pages API недоступен в CE (issue makeplane/plane#8986), страницы только руками.
- Описание задачи молча перезаписывается устаревшим состоянием открытого браузера (makeplane/plane#9995, оставлен комментарий с воспроизведением). Работа через API для описаний ненадёжна.
- Desktop-клиент только для Commercial.

## Решение: It's a Plan (2026-11-06)

Выбран [It's a Plan](https://itsaplan.dev) (AGPL-3.0, Community бесплатный), проверен локально. Интерфейс устраивает, строгое разделение по проектам принято.

Локальный запуск, остановка, бэкап и обновление: [issue-tracking/README.md](issue-tracking/README.md) (скрипт `issue-tracking/itsaplan.sh`). Web `localhost:3001`, API `localhost:3000` (справочник `/docs`, заголовок `x-api-key`). Регистрацию можно закрыть в god mode (Authentication).

### Как модель легла на It's a Plan

- Проекты (INFRA, GITOPS, PLANE, WIKI, WEB, MAP) в одной команде.
- Модули Plane стали **initiatives**. Одна задача входит ровно в одну initiative, поэтому initiative не подходит под релиз.
- **Релиз = custom field `Release`** (select: 0.1.0 … 1.0.0) в проекте. На каждый релиз вьюха и дашборд с фильтром по полю: счётчики (всего, готово, в работе, не начато) и список задач.
- Страницы Metadata и Releases: документы проекта (Docs), есть API.

### Ограничения и находки

- Сквозных (между проектами) вьюх и дашбордов в Community нет (workspace dashboard только в Pro). Срез по версии поперёк проектов нужно собирать скриптом через API.
- Фильтры есть только у виджетов Stat и Recent issues. У Breakdown и Burnup их нет.
- Custom fields создаются для проекта, на каждый проект отдельно.
- Встроенный импорт из Plane требует https и не переносит модули, поля и страницы. Перенос выполнен скриптом (чтение из БД Plane, запись через API It's a Plan): 6 проектов, 43 initiatives, 24 активные задачи PLANE. 65 архивных задач не переносились.
- Проект молодой (быстрые релизы, есть security advisories, breaking changes возможны): держать версию и бэкапы.
